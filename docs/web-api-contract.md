# Web control panel API contract

Base: `/api/v1`. JSON in, JSON out. Every route needs `Authorization: Bearer <BYTE_API_TOKEN>`
(missing/wrong = `401 {"detail": ...}`). The static UI (`web/`, served at `/`) is public and
holds no data. Chat stays `POST /messages` (unchanged).

Names (`lights`, `climate`, music `device`) are the configured device names returned by the GET
routes. Never send raw device or spreadsheet ids; an unknown name is `422`.

## Reads (never ask for confirmation)

| Route | Response |
|---|---|
| `GET /state` | `{lights: Light[]\|null, climates: Climate[]\|null, music: Music\|null, pending_confirmation: {summary}\|null, errors: string[]}`. A section whose adapter failed is `null` and its name is listed in `errors`. |
| `GET /lights` | `{lights: Light[]}` |
| `GET /climate` | `{climates: Climate[]}` |
| `GET /music/state` | `Music` |
| `GET /music/devices` | `{devices: [{name, active, volume: int\|null}], default: string\|null}`. `default` is `BYTE_SPOTIFY_DEVICE`. An empty `devices` list is valid (Spotify closed everywhere), not an error. |
| `GET /music/search?q=<1-200 chars>&kind=track\|album\|playlist\|artist` (kind default `track`) | `{items: MusicItem[]}` |
| `GET /music/playlists` | `{items: MusicItem[]}` |
| `GET /agenda?date=YYYY-MM-DD` | `{events: Event[]}` |
| `GET /finance/expenses?year=2026&month=10` | `{expenses: Expense[], total_cents: int}` |
| `GET /weather` | `{is_home, home: {name, region, country, label}\|null, forecast: Forecast\|null, home_now: Current\|null, errors: string[]}`. `forecast` is the city the panel shows (home unless the owner asked Byte to show another); `home_now` is the home city's current weather, for the bar chip. Each fails on its own: `null` plus `"forecast"` / `"home"` in `errors`, still 200. |
| `GET /reminders` | `{reminders: Reminder[]}`, soonest first. Calendar warnings are left out (the agenda shows the events). A reminder stays listed after its time until the device has played it and acked. |

## Actions

All send only the fields to change (omit the rest; unknown fields are `422`).

| Route | Body |
|---|---|
| `PATCH /lights/{name}` | `{power?, brightness?, color_temperature?, hue?, saturation?, timer_minutes?, do_not_disturb?}` |
| `PATCH /climate/{name}` | `{power?, mode?, target_temperature? (18-30, whole degrees), fan_speed?, swing?, power_save?}` |
| `POST /music/play` | `{uri?, device?}`. `uri` must come from `/music/search` or `/music/playlists`; omit to resume. |
| `POST /music/device` | `{name}`. Transfers playback to a device from `GET /music/devices` (case-insensitive). Keeps playing only if it was playing. Returns `Action` (`done`). Unknown name: `422 {"detail": "Aparelho desconhecido: <name>"}`. Raw ids are never accepted. Drops any pending confirmation like other actions. |
| `POST /music/control` | `{paused?, volume?, shuffle?, repeat?, skip?: "next"\|"previous"}` |
| `POST /agenda` | `{title, start (ISO 8601), duration_minutes (>0)}` |
| `DELETE /agenda/{event_id}` | none. Always asks confirmation. |
| `POST /finance/expenses` | `{amount_cents (>0), category, description, date}`. Always asks confirmation. |
| `POST /reminders` | `{text (1-200), at (ISO 8601, future), kind: "lembrete"\|"alarme"}`. A past time is `422`. |
| `DELETE /reminders/{id}` | none. Unknown id is `422`. |

Response (`200`), shape `Action`:

```
{"status": "done" | "pending_confirmation" | "cancelled", "message": string,
 "pending_confirmation": {"summary": string} | null}
```

- `done`: it ran; `message` is the human text of the result. Refetch the relevant GET.
- `pending_confirmation`: nothing ran. `summary` is generated by the server (for agenda deletes it names the event title, e.g. `Apagar o evento "Dentista"`); show it and offer
  Confirm / Cancel. Asks for: `DELETE /agenda/*` and `POST /finance/expenses`. Lights, climate and music
  never ask.

## Confirmation

`POST /confirm` with `{"approve": true | false}`.

- `true`: runs the pending action (`done`) or `409` if nothing is pending / it expired.
- `false`: drops it (`cancelled`).

Rules (enforced by the server, same store as chat): one pending action for the whole panel;
it lives 60 s; **any other action request (PATCH/POST/DELETE) drops it** before the new one
is evaluated; it can only be confirmed through `/confirm`, never by re-sending the action.

## Errors

| Status | When |
|---|---|
| 401 | missing/invalid bearer token |
| 409 | `/confirm` with nothing pending or expired |
| 422 | invalid body/query, unknown device name or event id (`DELETE /agenda/{id}` checks it up front, nothing becomes pending), climate adjustment while the unit is off (turn it on first; a body with `power: true` plus settings is fine), tool refused (e.g. unknown music uri); `{"detail": string}` |
| 422 (music) | Device offline / no active device, for `POST /music/play`, `/music/control` and `/music/device`: the `detail` is ready to show, in pt-BR, e.g. `BatCaverna está offline no Spotify. Abra o Spotify nele e tente de novo.` (uses `BYTE_SPOTIFY_DEVICE`; without it: `Nenhum aparelho ativo no Spotify. ...`). |
| 500 | `{"detail": "Internal error"}` (also an upstream device/provider failing on a read) |
| 504 | action timed out: `{"detail": "estado desconhecido: ..."}`. State unknown: re-read before retrying. |

## Voice (`WS /api/v1/live`)

Same socket and protocol as the ESP32 and the laptop client (spec §3, "Protocol"). The browser
cannot set `Authorization` on a WebSocket, and the token never goes in the URL, so the panel
authenticates with the **subprotocol**:

```js
new WebSocket('wss://<host>/api/v1/live', ['bearer', token]);  // Sec-WebSocket-Protocol: bearer, <token>
```

- Exactly two offered subprotocols, `bearer` first; the second is compared with
  `hmac.compare_digest` (same `token_matches` path as the header). The server accepts with the
  subprotocol `bearer` only, never echoing the token. Anything else closes before accept (the
  browser sees 1006 without `onopen`). The token must be made of token characters (letters,
  digits, `-_.~!#$%&'*+^|`), which `secrets.token_urlsafe` / hex tokens are.
- `Authorization: Bearer <token>` keeps working for the ESP32 and `voice/` (no subprotocol echoed).
- Client: first frame `{"type":"start","segment":"auto","conversation_id"?}` (the chat's id, so
  chat and voice share one conversation); mic audio is buffered (5 s cap) until `ready`; then
  PCM16 mono 24 kHz little-endian binary frames both ways (40 ms frames up). Events used:
  `ready`, `transcript {role, text}` (shown in the chat box), `interrupt` (flush playback, reply
  `{"type":"played","audio_end_ms"}`), `turn_done`, `error {code}`, `closed`. Close 4000 means
  another client took over: the panel says so and does not reconnect.
- Half-duplex by default like `voice/` (mic ignored while Byte talks; `BARGE_IN` in `web/live.js`).
  The panel closes the session 12 s (counted after Byte finishes speaking) after `ready` or `turn_done` with no speech; the server's own
  60 s idle and 10 min cap still apply.
- Wake word "Ei Byte" runs in the browser: `web/models/{melspectrogram,embedding_model}.onnx`
  (from the openwakeword package) + `ei_byte.onnx` (copy of `models/ei_byte.onnx`, retrain means
  re-copy), threshold 0.5, onnxruntime-web loaded from jsDelivr when "escuta ativa" is turned on.
  No audio leaves the browser until the wake word fires.
- **Secure context required** for the microphone: `http://127.0.0.1` / `localhost` work; a LAN
  address needs TLS (`https://` + `wss://`, see Safety in `CLAUDE.md`).

## Projects terminal (`WS /api/v1/ws/terminal`, Spec 4)

The panel marks itself so it alone gets `open_project` / `close_project`: `POST /messages` and
the `/live` start frame carry `"client": "panel"` (any other client omits it; an unknown value
is 422 / `bad_start`). Routing, not security: every client holds the same token.

- Auth like `/live` (header or `["bearer", token]` subprotocol). One panel at a time: a new
  connection closes the old one with 4000. Closed with 1008 when this server has no terminal
  (no `BYTE_PROJECTS`, no `claude` on `PATH`, or no pty extra — e.g. the Docker image).
- Server → panel: text `{"type":"state","project":"FinFlow"|null}` on connect and on every
  open, close or exit of `claude`; binary frames = raw terminal output. On connect with a
  project open, the scrollback (~256 KB) is replayed right after `state`.
- Panel → server: binary frames = keystrokes (UTF-8); text
  `{"type":"resize","cols":n,"rows":n}` (clamped to 2..500). Anything else is ignored; input
  with no project open is dropped.
- The `claude` process belongs to the server: closing or reloading the tab leaves it running.
  It starts in the project folder without any `BYTE_*` variable or provider key in its
  environment. Nothing typed or printed is logged.

## Lynus (Spec 5)

Lynus is a second agent (Google's coding model) that drives the open project's `claude` on its
own: it writes the prompts, **approves every permission request by itself**, reviews each reply
against the project's specs and plans, and stops when the task is done.

- Hand-over: the panel sends Byte `Quero passar uma tarefa para o Lynus.` (`POST /messages`,
  `client: "panel"`). Byte asks for the project and a short task, then calls `start_lynus`
  (panel only), which opens a **fresh** `claude` in that project (`--permission-mode default`).
- `GET /lynus` → `{phase, project, task, turns, notes: [{role, text, at}]}`. `phase`:
  `off | briefing | working | done | stopped | failed`; `briefing` is Lynus talking with the
  owner, `working` is Lynus on its own. `role`: `owner | lynus | system | claude` (`claude` =
  a prompt Lynus sent to Claude). Last 200 notes.
- `POST /lynus/messages {content}` (1–4,000 chars) → `202`. Lynus answers through a push.
  `409` outside `briefing`/`working`.
- `POST /lynus/stop` → `{phase}`. Drops autopilot and sends `Esc` to Claude. The terminal stays.
- `503` on every Lynus route when the server has no project terminal or no `BYTE_GEMINI_API_KEY`.
- `POST /claude/hooks` is **not** for the panel: only the `claude` process calls it, with its
  own per-session token. The owner token is refused there.

## Panel pushes (`WS /api/v1/ws/panel`, Spec 6)

- Auth like `/ws/terminal` (header or `["bearer", token]` subprotocol). One panel at a time: a
  new connection closes the old one with 4000 (do not reconnect after 4000 or 1008).
- Server → panel: text `{"type":"lynus"}` whenever Lynus's phase or notes change; reload
  `GET /lynus`.
- Server → panel: text `{"type":"weather"}` whenever the shown city changes — by `show_weather`
  from any client (panel chat, panel voice, the ESP32) or by `DELETE /weather/display`. No data:
  the panel reloads `GET /weather`. Reload it on every (re)connect too, so a change made while
  disconnected is not missed. Anything the panel sends is ignored.
- `DELETE /weather/display` runs `show_weather` with no city through `ToolRunner` (back to home)
  and answers with the `GET /weather` body.

## Music ducking during voice

While a `/live` session is open (from `ready` until it ends for any reason) the server lowers
Spotify to `BYTE_LIVE_DUCK_PERCENT` (default 20, `0..100`; `100` disables ducking) and restores
it afterwards. The panel does nothing: it only sees `volume` change in `GET /music/state`.

- Restored to the volume at session start, unless the agent set a volume during the session
  through `control_music` (voice or `POST /music/control`): that value wins.
- Skipped silently when nothing is playing, no device, volume already at or below the duck, or
  any music error (never fails the session). Restore is shielded from cancellation (socket drop,
  replacement with code 4000, timeout). A replacement session keeps the original volume.
- Expect `volume` to read ~20 while the mic session is open, and a short lag (Spotify ~1 s).

## Logs

`tool.failed` carries `reason`: `guard` (safety rule, e.g. lamp toggled twice, unknown music
uri), `offline` (no reachable playback device), `validation` (bad argument, unknown device or
event) or `upstream` (anything else, including vendor failures). No content is logged.

## Static UI

`web/` is mounted at `/` (public, `index.html` fallback) only when the directory exists.
Everything the UI shows must come from `/api/v1/*` with the token.
